# Plan: Realtime Data Plot Panel (third panel)

## Behavior (confirmed)
- New **Plot** panel alongside Pilot and Data (PanelSwitcher gains a third entry).
- Select any number of monitor channels (kernel / device / extra headers, unlimited).
- **Recording** streams curves; x-axis = **step index** (one recorded sample = one step), window = `[currentIdx - horizon, currentIdx]`.
- **Pause/Stop** freezes the plot (still pannable/zoomable); **Resume** continues; recording runs in background while you switch to Pilot/Data.
- **When recording is stopped, a Save button appears**: saves locally to `Downloads/Bitbot/` via MediaStore (no permission needed, minSdk 31) as
  - **CSV** — header row `step,<channel names>`, one row per recorded sample (channels added mid-recording get empty cells), for Python/Excel analysis;
  - **PNG** — snapshot of the plot exactly as drawn (Compose GraphicsLayer record → Bitmap → PNG).
  Filename `bitbot_plot_yyyyMMdd_HHmmss.{csv,png}`, toast confirms the path.
- Pan/zoom both axes; follow-latest and auto-fit-Y with one-tap re-enable; legend chips name each colored curve (tap = show/hide).
- Sample rate (2/5/10/20/50 Hz) and horizon (~10 s–10 min) configurable.

## Non-negotiable per your note: exactly one data-request stream
The backend sends one `monitor_data` reply per `request_data` with no per-client tagging, so parallel loops would interleave and corrupt sample cadence. Therefore:
- `WebSocketClient` gets a **refcounted single poll loop**: `acquirePolling(rateHz)`/`releasePolling(handle)`. One loop exists app-wide, running at the **max** requested rate; it re-reads the current socket every tick (also fixes a latent bug: today's loop captures the socket at start and goes stale after auto-reconnect).
- Data panel acquires at 10 Hz once (init/onCleared), no re-acquire on reconnect; its table throttles `monitorData` via `.sample(100ms)` so a faster recorder poll doesn't re-render the table at 50 Hz.
